## Введение

Система веб-отчётов позволяет генерировать аналитические отчёты по данным игр через простой диалог с AI-агентом. Вы описываете что хотите увидеть на естественном языке, а система автоматически создаёт соответствующий отчёт.

### Основные возможности

- 💬 **Диалог с AI**: Описывайте требования к отчёту на русском языке
- 📊 **Визуализация**: Таблицы, графики, метрики
- 📥 **Экспорт**: Сохранение отчётов в CSV
- 🔄 **История**: Сохранение и просмотр истории диалогов
- 🎯 **Гибкость**: Различные типы запросов и отчётов

## Знания о предметной области (для оператора)

Этот раздел предназначен для оператора, который обслуживает развёртывание и редактирует файлы знаний. Пользователю чата ничего здесь менять не нужно: он задаёт вопросы в интерфейсе, а агент читает подготовленные оператором темы.

### Структура папки

Знания читаются один раз при запуске backend. По умолчанию `knowledge_dir` ведёт к поставляемой папке `bd_shared/knowledge/bez_durakov`:

```text
bd_shared/
└── knowledge/
    └── bez_durakov/
        ├── manifest.toml
        ├── glossary.md
        ├── rules.md
        └── scoring.md
```

В корне папки обязателен `manifest.toml`. Каждый обычный файл `.md` в этом корне становится темой, скрытые файлы пропускаются, а подкаталог делает папку недействительной. Поставляемый `bd_shared/knowledge/bez_durakov/rules.md` является скелетом, который оператор заполняет настоящими правилами. Ни изменения кода, ни новый деплой для этого не нужны, после сохранения достаточно перезапустить стек.

### Манифест

`manifest.toml` содержит ровно два ключа. Любой дополнительный ключ отклоняется.

- `dataset` соответствует имени настроенной базы данных. Значение должно полностью соответствовать шаблону `^[a-z0-9_-]{1,64}$`, состоять из строчных латинских букв, цифр, `_` или `-` и совпадать с именем базы данных. В поставляемом примере это `bez_durakov`.
- `persona` задаёт роль, тон и язык ответов агента. Это непустая строка длиной не более `knowledge_max_persona_chars` символов.

Например:

```toml
dataset = "bez_durakov"
persona = """Ты аналитик данных. Отвечай по-русски."""
```

`persona` задаёт общую манеру ответа. Подробные правила предметной области остаются в теме `rules.md`.

### Темы, идентификаторы и краткое описание

Имя файла задаёт идентификатор темы. У файла `rules.md` идентификатор `rules`; часть имени до `.md` должна полностью соответствовать `^[a-z0-9_-]{1,40}$`. Прописные буквы, пробелы и другие символы недопустимы.

Заголовок темы берётся из первой строки, которая соответствует `^#{1,6}\s+\S`. Из неё удаляются только начальные `#` и окружающие пробелы. Получившийся заголовок не может быть длиннее `knowledge_max_title_chars` символов.

Первый непустой блок после этого заголовка становится кратким описанием темы. Пустые строки перед ним пропускаются, а строки блока соединяются одним пробелом. Его длина не может быть больше `knowledge_max_summary_chars` символов. Первой строкой этого блока должен быть обычный текст. Если после заголовка первым непустым блоком идёт список, нумерованный список, ограждение кода, таблица, цитата, новый заголовок или HTML-блок, документ будет отклонён. Поэтому сразу после заголовка не ставьте список, кодовый блок, таблицу, цитату или заголовок.

```markdown
# Название темы

Первый простой абзац становится кратким описанием темы.

Далее можно добавить подробности, примеры и разделы.
```

### Настройки `[dataset]`

В `bd_shared/config.toml` раздел `[dataset]` задаёт, какие данные обслуживает backend:

| Ключ | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `tools_module` | `"bd_shared.tools.bez_durakov"` | Точка импорта модуля с фабрикой `build_service(engine)`. Пустое значение прерывает запуск и preflight. |
| `knowledge_dir` | `"knowledge/bez_durakov"` | Путь к папке знаний относительно `bd_shared`; пустое значение отключает загрузку знаний. |

### Пределы знаний в `[webreport]`

| Ключ | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `knowledge_max_title_chars` | `80` | Максимальная длина заголовка темы. |
| `knowledge_max_summary_chars` | `200` | Максимальная длина первого абзаца, который становится кратким описанием. |
| `knowledge_max_persona_chars` | `2000` | Максимальная длина `persona` в манифесте. |
| `knowledge_max_topics` | `50` | Максимальное число файлов тем. |
| `knowledge_max_doc_bytes` | `65536` | Максимальный размер одного файла темы в байтах. |
| `knowledge_max_bytes_per_turn` | `131072` | Суммарный лимит байтов документов, прочитанных за один вопрос пользователя, когда вопрос охватывает несколько больших тем. |

Все шесть пределов читаются из текущей конфигурации; значение `131072` для `knowledge_max_bytes_per_turn` сохраняет прежний лимит по умолчанию. Ключ `knowledge_dir` переехал в раздел `[dataset]`, и если он остался в `[webreport]`, запуск прерывается сообщением, называющим оба места.

### Проверка, безопасный перезапуск и восстановление

После любого изменения папки знаний **до перезапуска** запустите из корня репозитория:

```bash
make validate-knowledge
```

Команда запускает настоящий загрузчик внутри образа backend с `--no-deps`, поэтому проверка использует те же Docker-конфигурацию, путь и имя базы данных, что и backend, но не требует запущенных MySQL или LiteLLM.

`make restart` и `make rebuild` теперь сами выполняют эту проверку первой. Если папка недействительна, команда завершается до `docker compose up --force-recreate` или `docker compose down`: работающий исправный контейнер не заменяется и не останавливается.

Например, при проверке тестовой папки с кратким описанием длиной 201 символ выводится реальная ошибка:

```text
Knowledge folder is invalid: Knowledge document summary exceeds 200 characters: /bd_shared/knowledge/_todo69_bad/rules.md; summary is 201 characters, limit is 200
```

Путь указывает файл, а `summary is 201 characters, limit is 200` показывает наблюдаемую и разрешённую длину. В этом случае сократите первый простой абзац после заголовка до 200 символов или меньше и снова выполните `make validate-knowledge`.

Если backend уже не запускается, восстановите последнюю заведомо исправную версию папки, затем выполните `make validate-knowledge` и `make restart`. Если восстановить папку сразу нельзя, верните сервис без знаний следующим аварийным путём:

1. В активной конфигурации (`bd_shared/config.local.toml`, если используется локальное переопределение, иначе `bd_shared/config.toml`) установите:

   ```toml
   [webreport]
   knowledge_dir = ""
   ```

2. Из корня репозитория выполните команды именно в этом порядке:

   ```bash
   make validate-knowledge
   make restart
   curl --retry 30 --retry-all-errors --retry-delay 1 --retry-max-time 60 --fail http://127.0.0.1:28000/health
   ```

Пустое значение является штатным отключением знаний: проверка печатает предупреждение и завершается с кодом 0, после чего перезапуск восстанавливает сервис. Затем исправьте или восстановите папку, верните её путь в `knowledge_dir`, ещё раз выполните `make validate-knowledge` и только после успешной проверки — `make restart`.

### Ручная проверка получения знаний на настоящей модели

Эту проверку выполняют после смены модели или обновления LiteLLM. Она намеренно не входит в `make test`: нужны действующий API-ключ и доступная через proxy настоящая модель. На время проверки временная тема попадает в общий system prompt, поэтому проводите её в окно обслуживания и не смешивайте контрольные запросы с пользовательскими сессиями.

1. Убедитесь, что backend работает в режиме `agent`, а `/health` показывает исправный LiteLLM. Создайте резервную копию папки знаний **до** первого изменения:

   ```bash
   topic_dir=bd_shared/knowledge/bez_durakov
   backup_dir="$(mktemp -d)"
   cp -a "$topic_dir/." "$backup_dir/"
   (cd webreport && docker compose logs backend | grep 'LLM mode elected: agent')
   curl --fail http://127.0.0.1:28000/health
   ```

2. Сгенерируйте новый непредсказуемый маркер и создайте отдельную тему `live-model-release-check.md`. Маркер запрещено помещать в первый абзац: этот абзац становится кратким описанием в system prompt, а проверяемый факт должен быть доступен только через `read_knowledge`.

   ```bash
   export NONCE="BD72-$(python3 -c 'import secrets; print(secrets.token_hex(16).upper())')"
   python3 - <<'PY'
   import os
   from pathlib import Path

   nonce = os.environ["NONCE"]
   Path("bd_shared/knowledge/bez_durakov/live-model-release-check.md").write_text(
       "# Проверка чтения временной темы\n\n"
       "Эта временная тема хранит контрольный маркер для ручной проверки "
       "получения знаний моделью после смены модели.\n\n"
       "## Контрольный факт\n\n"
       f"Точный контрольный маркер этой проверки: `{nonce}`.\n",
       encoding="utf-8",
   )
   PY
   make restart
   curl --retry 30 --retry-all-errors --retry-delay 1 --retry-max-time 60 \
     --fail http://127.0.0.1:28000/health
   ```

3. Отправьте запрос с новым `session_id`, чтобы сохранённая история другой проверки не раскрыла маркер:

   ```json
   {
     "message": "Какой точный контрольный маркер указан во временной теме «Проверка чтения временной темы»? Приведи его без изменений и кратко поясни, откуда он взят.",
     "session_id": "todo72-happy-<новый-uuid>"
   }
   ```

   Выполните `POST http://127.0.0.1:28000/api/chat` с `Content-Type: application/json`. Успешный результат обязан одновременно удовлетворять всем условиям:

   - `success` равно `true`, а `mode` равно `agent`;
   - в `query_info` есть `{"tool":"read_knowledge","args":{"topic":"live-model-release-check"}}`;
   - `message` содержит точное значение `$NONCE`;
   - ответ написан по-русски, кратко и фактологично, в соответствии с `persona` из манифеста.

   Наличие маркера без вызова `read_knowledge` не считается доказательством: модель могла получить его из краткого описания.

4. В отдельной новой сессии задайте вопрос, не покрытый ни одной темой, например: `Какой сегодня уровень прилива в вымышленном океане планеты Зета-9? Если данных нет, скажи об этом прямо.` Ответ должен быть по-русски, а среди элементов `query_info` не должно быть ни одного вызова `read_knowledge`. Любой такой вызов означает провал проверки нерефлексивного retrieval; остановите релиз и зафиксируйте точный запрос, ответ и модель вместо изменения prompt вслепую.

5. Для отрицательного контроля **не удаляйте тему**. Сохраните имя файла, идентификатор, заголовок и первый абзац без изменений, а замените только абзац тела с маркером, например на:

   ```markdown
   Контрольный маркер в отрицательной контрольной версии отсутствует.
   ```

   Выполните `make restart`, дождитесь исправного `/health` и повторите запрос из пункта 3 с ещё одним новым `session_id`. Старое значение `$NONCE` обязано отсутствовать в `message`. Сохранённый первый абзац изолирует источник факта: между двумя запусками изменилось только содержимое, доступное через `read_knowledge`.

6. Запишите в `.omo/evidence/operator-knowledge-folder/72-happy.txt` и `72-failure.txt` точные команды, тела запросов, ответы `/api/chat`, проверки условий и фрагменты `docker compose logs backend`. Длинный вывод захватывайте механически через Python, без shell-перенаправления; каждый блок должен заканчиваться явным кодом возврата:

   ```python
   import shlex
   import subprocess
   from pathlib import Path

   def capture(evidence_path, command, cwd=None):
       result = subprocess.run(
           command,
           cwd=cwd,
           text=True,
           stdout=subprocess.PIPE,
           stderr=subprocess.STDOUT,
       )
       output = result.stdout
       if output and not output.endswith("\n"):
           output += "\n"
       with Path(evidence_path).open("a", encoding="utf-8") as stream:
           stream.write(f"$ {shlex.join(command)}\n{output}exit={result.returncode}\n")
       return result
   ```

7. Восстановите исходную поставляемую конфигурацию независимо от результата проверки: удалите только временную тему, сравните `manifest.toml`, `rules.md`, `scoring.md` и `glossary.md` с резервной копией, затем перезапустите backend уже с тремя исходными темами. Завершайте проверку только после обеих команд:

   ```bash
   rm bd_shared/knowledge/bez_durakov/live-model-release-check.md
   diff -qr "$backup_dir" "$topic_dir"
   make restart
   cd webreport && docker compose ps
   curl --fail http://127.0.0.1:28000/health
   ```

### Сообщения при запуске

Папка отсутствует или не настроена, backend продолжает работу без знаний. Папка с ошибкой манифеста или документа останавливает запуск. В логах используются следующие точные шаблоны:

| Ситуация | Строка лога | Результат |
| --- | --- | --- |
| `knowledge_dir` не задан | `Knowledge folder is not configured (dataset.knowledge_dir is unset); the agent runs without dataset knowledge.` | Запуск продолжается без знаний. |
| Папка по указанному пути не найдена | `Knowledge folder not found at %s; the agent runs without dataset knowledge.` | Запуск продолжается без знаний. |
| Манифест или тема не прошли проверку | `Knowledge folder is invalid: %s` | Запуск прерывается. |

В шаблонах `%s` заменяется фактическим путём или подробностью ошибки. После успешной загрузки будет информационная строка `Knowledge loaded: dataset=%s, topics=%d`.

## Инструмент доступа к данным (для оператора)

Backend не знает вашу предметную область. Он узнаёт её из одного Python-модуля, который вы
пишете сами, и из папки знаний. Чтобы направить систему на другую базу, нужно поменять два
раздела конфигурации и поставить два артефакта, менять код backend не требуется.

### Контракт модуля

Модуль называется дотированным путём импорта в ключе `dataset.tools_module`. Он обязан
предоставить функцию с фиксированным именем `build_service`:

> **Это доверенный вход.** Backend импортирует указанный модуль при запуске и выполняет его код
> внутри своего контейнера. Право записи в `config.local.toml` тем самым равносильно праву
> выполнять код в контейнере backend, а не только праву выбрать базу данных. Относитесь к этому
> ключу так же, как к строке подключения: он не рассчитан на недоверенный ввод.

```python
from sqlalchemy import Engine


def build_service(engine: Engine) -> object:
    """Собрать объект-сервис вокруг внедрённого движка."""
    return StationService(engine)
```

Функция получает уже готовый движок и обязана вернуть объект, не открывая соединение. Это
позволяет проверять модуль с остановленной базой.

### Что становится инструментом

Каждый публичный метод возвращённого объекта становится инструментом агента. Имя инструмента
равно имени метода, описание берётся из первого абзаца docstring, а схема аргументов
строится из аннотаций типов. Действуют три правила:

- вспомогательный метод, который не должен быть инструментом, получает имя с ведущим
  подчёркиванием;
- `property` инструментом не становится никогда и не вычисляется при обнаружении;
- публичный атрибут, который не является вызываемым, молча пропускается;
- обнаружение обходит `dir()`, поэтому унаследованные публичные методы тоже становятся
  инструментами. Если вы наследуете сервис от базового класса, унаследованный публичный метод
  без docstring или без аннотаций прервёт запуск. Наследуйтесь от `object` либо давайте
  унаследованным помощникам имена с ведущим подчёркиванием.

Аннотации параметров ограничены значениями, выразимыми в JSON: `str`, `int`, `float`, `bool`,
`datetime.date`, `datetime.datetime`, а также `X | None` от любого из них.

Запуск прерывается одной строкой, называющей и модуль, и метод, если у метода нет docstring,
если у параметра нет аннотации, если аннотация вне поддерживаемого набора, если имя метода
входит в зарезервированный набор (`read_rows`, `mark_report`, `read_knowledge`), если параметр
переменный (`*args` или `**kwargs`), или если параметр позиционный-только (объявлен до `/`).
Две последние формы отвергаются потому, что инструмент всегда вызывается именованными
аргументами: иначе метод прошёл бы обнаружение и падал бы при каждом вызове.

Аннотация возвращаемого значения ни на что не влияет и не проверяется.

### Что метод может возвращать

Принимаются три формы: `DataFrame`, словарь и список. Любая другая форма становится
сообщением `Tool error`.

- `DataFrame` превращается в записи с колонками кадра;
- словарь становится одной записью с ключами словаря;
- список значений превращается в записи с одной синтезированной колонкой `item`, потому что у
  голого списка нет собственного имени колонки.

Последнее стоит учесть при переносе: в этом развёртывании `get_games_by_date_range` возвращает
список идентификаторов, и его записи теперь приходят как `{"item": 11}`, а не `{"game_id": 11}`.
Имя `item` нейтрально намеренно, чтобы синтезированная колонка не совпала с настоящей колонкой
чужой таблицы. Если вам нужно осмысленное имя, возвращайте `DataFrame` или список словарей.

### Как писать запросы внутри модуля

Внутри модуля разрешён любой стиль работы с SQLAlchemy: Core, ORM `Session`,
`pandas.read_sql` или параметризованный текстовый SQL. Единственное ограничение в том, что
модуль не строит собственное подключение, а работает с внедрённым движком.

### Режим только для чтения

Backend строит ровно один движок и делает его доступным только для чтения на момент
установления соединения:

| Диалект | Механизм |
| --- | --- |
| PostgreSQL | параметр подключения `options=-c default_transaction_read_only=on` |
| SQLite | форма файлового URI `mode=ro`, файл открывается только для чтения самой ОС |
| MySQL | `SET SESSION TRANSACTION READ ONLY` в обработчике `connect` |
| MariaDB | та же инструкция, что и для MySQL |

Для диалекта вне этого набора backend не применяет обёртку, ничего не предупреждает и ничего
не запрещает: режим только для чтения тогда полностью зависит от прав учётной записи.

Строка `mariadb://` получает собственное имя диалекта и не наследует запись MySQL, поэтому она
указана отдельно. В отличие от остальных трёх, эта запись не подтверждена в репозитории
автоматическим тестом на отказ в записи против живого сервера MariaDB. Если сервер не примет
инструкцию, запуск завершится ошибкой при первом подключении, то есть громко, а не тихим
разрешением записи.

Две честные границы. На MySQL и PostgreSQL это свойство сессии, поэтому модуль, который
намеренно выполнит `SET SESSION TRANSACTION READ WRITE` или `SET default_transaction_read_only
= off`, может его снять; вне досягаемости модуля только файловый режим SQLite. Поэтому вторым
слоем рекомендуется выдать backend отдельную учётную запись только для чтения.

Отказ в записи доходит до модели как обычный текст инструмента вида
`Tool error: Tool 'insert_reading' failed: ...`, а не как падение процесса.

### Проверка модуля до запуска

```bash
make -C webreport validate-tools
```

Команда импортирует модуль, вызывает фабрику и печатает одну строку со списком найденных
инструментов либо одну строку ошибки, называющую модуль и проблемный метод. Соединение при
этом не открывается, поэтому проверка работает и с остановленной базой. `make restart` и
`make rebuild` запускают её рядом с `make validate-knowledge`.

### Имя набора данных и форма URL

Имя набора данных выводится из `[database].url` без обращения к базе. Для серверного URL это
имя базы из URL, для файлового это основа имени файла: `sqlite:////data/library.db` даёт
`library`. Это же имя должно стоять в поле `dataset` файла `manifest.toml` папки знаний.

Две формы URL отвергаются при загрузке конфигурации: `sqlite://` без файла и
`sqlite:///:memory:`. In-memory SQLite не поддерживается.

Для SQLite указывайте абсолютный путь. Под `uri=true` драйвер разрешает относительный путь
относительно рабочего каталога процесса на момент подключения, а не на момент построения
движка.

### Что происходит при недоступности базы или модели

Если база недоступна, backend делает пять попыток подключения с интервалом две секунды,
затем печатает одну строку вида
`Database is unreachable after 5 attempts: dialect=... host=... port=... database=... reason=...`
и завершает запуск с ненулевым кодом. Строка не содержит учётных данных. Контейнер с
`restart: unless-stopped` будет поднят снова.

Если недоступна модель, процесс остаётся запущенным, но отказывается отвечать: `/health` и
`/api/chat` возвращают 503. Каждая следующая попытка чата повторяет проверку ровно один раз,
и первый успешный результат собирает агента и отвечает на этот же запрос.

### Замечание о встроенном MySQL

Если настроенный URL не MySQL, встроенный сервис MySQL из `docker-compose.yml` всё равно
поднимается, но получает значения-заглушки в `.env.mysql`, к которым никто не подключается.

**Q: Система работает без доступной языковой модели?**

A: Нет. Без доступной модели backend остаётся запущенным, но отказывается отвечать: `/health` и `/api/chat` возвращают 503 с одним русским предложением. Как только модель становится доступна, первая же следующая попытка чата её обнаруживает и отвечает на этот запрос, перезапуск не нужен.

### Технические вопросы

**Q: Backend не запускается**

A: Проверьте:
1. Docker контейнеры запущены: `docker compose ps`
2. Логи контейнера: `make logs` или `docker compose logs backend`
3. Контейнер MySQL доступен backend по имени `mysql` на порту `3306`
4. Файл bd_shared/config.toml существует в родительской директории

**Q: Frontend показывает "API недоступен"**

A: 
1. Проверьте статус backend: `curl http://localhost:28000/health`
2. Проверьте контейнеры: `docker compose ps`
3. Посмотрите логи: `docker compose logs frontend`
4. Перезапустите: `make restart`

**Q: Ошибка "Database connection failed"**

A:
1. Проверьте сервис MySQL: `docker compose ps mysql`
2. Проверьте настройки в `../bd_shared/config.toml`
3. Проверьте подключение из контейнера:
   ```bash
   docker compose exec backend python -c "import socket; print(socket.gethostbyname('mysql'))"
   ```

**Q: Как использовать с настоящими AI агентами?**

A:
1. Создайте `bd_shared/config.local.toml` из `config.local.toml.example`
2. Укажите ключ в `[webreport].openai_api_key` файла `bd_shared/config.local.toml`
3. Запустите или перезапустите стек: `make start` / `make restart`
4. Учтите, что Compose и service env-файлы генерируются `generate_env.py` из объединённых `bd_shared/config.toml` и `config.local.toml`
